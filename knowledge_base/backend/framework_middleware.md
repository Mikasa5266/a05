# 后端工程师 - 框架与中间件（知识点 + 题库）

## 一、知识点部分（问题 + 解析）

### 1. Spring Boot 自动配置的工作机制是什么？
**解析：**
核心是条件装配 + 约定优于配置。启动时根据 classpath、配置项和环境条件决定是否装配 Bean。开发效率高，但也要警惕隐式配置带来的可观测性不足。

### 2. IoC 与 AOP 分别解决什么问题？
**解析：**
IoC 解决对象创建和依赖管理，降低耦合；AOP 解决横切逻辑复用，如日志、鉴权、事务。两者结合可显著提升可维护性，但需注意代理链复杂度。

### 3. Go GMP 调度模型为什么适合高并发 I/O？
**解析：**
G（goroutine）轻量、M（线程）执行、P（处理器上下文）调度。相比一请求一线程，goroutine 切换成本更低，能在大量连接场景下提升并发容量。

### 4. Channel 使用中最常见的风险是什么？
**解析：**
常见风险包括死锁、goroutine 泄漏、向已关闭 channel 发送导致 panic。并发代码应明确谁关闭、何时关闭、谁消费完成。

### 5. 中间件链路设计为什么强调顺序？
**解析：**
鉴权、限流、日志、恢复、业务处理顺序不同会导致行为差异。比如 panic recovery 应在靠外层，鉴权通常早于业务逻辑。

### 简答题 3：请说明 Spring AOP 失效的常见原因及排查思路。
**参考答案：**
常见原因：
1. 目标方法非 public 或被 final 修饰；
2. 同类内部调用绕过代理；
3. 切点表达式未命中；
4. Bean 未被 Spring 容器管理。
排查可从代理类型、切点日志、Bean 生命周期三层定位。

**答案解析：** AOP 失效题本质考察代理机制理解，能讲出“自调用绕过代理”通常是高分点。

### 简答题 4：设计一个“限流 + 熔断 + 降级”中间件链路。
**参考答案：**
建议顺序：请求标识 -> 限流 -> 熔断状态检查 -> 业务处理 -> 错误分类 -> 降级响应。并记录限流命中率、熔断开关状态和降级比例。

**答案解析：** 这类题考察稳定性治理能力，不仅要会做功能，还要有可观测指标。

### 简答题 5：如何在 Go 服务中实现优雅停机？
**参考答案：**
1. 监听系统信号（SIGTERM/SIGINT）；
2. 停止接收新请求；
3. 设定超时等待在途请求完成；
4. 关闭连接池、后台任务和消息消费者；
5. 输出停机阶段日志。

**答案解析：** 优雅停机是生产可靠性基础能力，回答应覆盖“停止接入 + 排空 + 释放资源”。

### 简答题 6：如何防止中间件链变得不可维护？
**参考答案：**
可通过职责分层、顺序约定、配置化开关、统一上下文规范和链路测试来治理。避免在中间件中堆积过多业务逻辑。

**答案解析：** 中间件应以横切能力为主，业务逻辑应下沉到 service 层，才能长期演进。

## 三、扩展知识点（问题 + 解析）

### 6. Spring Bean 生命周期中哪些阶段最容易出现隐性问题？
**解析：**
常见问题集中在初始化与销毁阶段：
- 初始化顺序不一致导致依赖未就绪；
- 代理对象与原始对象混用导致行为不一致；
- 销毁阶段资源未释放导致连接泄漏。
线上稳定性问题常不是“代码不会写”，而是生命周期细节忽略。

### 7. 为什么说“配置中心治理”本质是发布治理的一部分？
**解析：**
配置变更会直接影响运行行为，和代码发布同样具备风险。配置中心应具备版本、审批、灰度、回滚、审计能力，否则容易出现“无代码变更但服务异常”。

### 8. Go 服务中 panic/recover 的边界应该怎么设计？
**解析：**
`recover` 适合在协程边界或请求边界做兜底，不应滥用到业务逻辑层吞掉错误。正确做法是：记录上下文、上报告警、返回可控错误，再按故障等级触发降级。

### 9. RPC 框架选型时为什么不能只看吞吐？
**解析：**
吞吐只是单维指标。实际还要看可观测性、协议兼容性、治理能力（重试、熔断、限流）、生态成熟度和团队维护成本。

### 10. 如何理解“幂等、重试、超时”三者的协同关系？
**解析：**
超时会触发重试，重试会导致重复请求，重复请求需要幂等兜底。三者必须整体设计，否则任一缺失都会放大系统风险。

### 11. 为什么异步任务系统必须有死信队列？
**解析：**
没有死信队列，异常消息会无限重试或直接丢失。死信机制可隔离异常消息并支持人工或自动补偿，是可靠异步系统的基础能力。

### 12. 服务注册发现中的“脑裂”会带来什么问题？
**解析：**
脑裂会导致节点状态视图不一致，出现错误路由、重复选主、流量倾斜等问题。需要通过一致性协议、健康检查策略和故障演练降低风险。

### 13. 熔断、限流、降级三者的职责边界是什么？
**解析：**
- 限流：在入口控制流量峰值；
- 熔断：在依赖异常时快速失败防扩散；
- 降级：在资源不足时提供可接受的兜底结果。
三者组合后，系统具备更强的故障自愈能力。

### 14. 线程池与协程池为什么都需要容量治理？
**解析：**
池化本质是资源复用，不是无限容量。若无上限与拒绝策略，会出现队列堆积、延迟抖动和级联超时。容量治理应结合压测与业务峰值。

### 15. 网关层统一鉴权的收益与风险分别是什么？
**解析：**
收益是能力集中、策略统一、审计方便；风险是网关成为关键单点和性能瓶颈。需要高可用部署、限流保护和旁路兜底。

### 简答题 9：如何评估一个中间件是否值得引入？
**参考答案：**
从收益、复杂度、性能开销、可观测性、团队维护成本五个维度评估；先在低风险场景试点，再决定是否全局推广。

**答案解析：** 中间件不是越多越好，需遵循“最小必要”原则。

### 简答题 10：请给出 RPC 超时与重试的推荐配置思路。
**参考答案：**
按调用链预算拆分总超时；区分读写接口重试策略；设置抖动退避和最大重试次数；禁止对非幂等写请求盲目重试。

**答案解析：** 该题核心是“预算化超时 + 受控重试 + 幂等约束”。

### 简答题 11：如何设计一个可回放的请求日志体系？
**参考答案：**
记录请求元信息、关键参数摘要、响应码、耗时、trace-id 和版本号；敏感信息脱敏；支持按时间窗与请求链回放。

**答案解析：** 可回放日志能显著提升线上问题复现与定位效率。

### 简答题 12：服务依赖方频繁抖动时，你会如何稳定本服务？
**参考答案：**
组合策略：短超时、限并发、熔断降级、本地缓存兜底、异步补偿；并通过隔离线程池避免抖动传染核心业务。

**答案解析：** 稳定性题重点是“多层防线”，单一策略往往不足。

### 简答题 13：如何在团队中落地“中间件开发规范”？
**参考答案：**
制定规范模板（输入输出、顺序、日志、监控、错误处理、性能预算），配套 Code Review 清单和自动化测试，确保新中间件可控演进。

**答案解析：** 工程规范是规模化协作的关键，能降低长期维护成本。

### 简答题 14：请说明“背压（Backpressure）”在服务治理中的意义。
**参考答案：**
背压用于在下游处理能力不足时向上游传递压力信号，避免无限堆积。可通过队列阈值、拒绝策略和速率反馈实现。

**答案解析：** 背压机制是高并发系统防雪崩的重要组成。

### 简答题 15：如何构建一个可观测的异步任务执行框架？
**参考答案：**
应包含任务状态机、重试与死信、执行耗时统计、失败分类、trace 关联和告警阈值配置；支持按任务类型做限速与隔离。

**答案解析：** 异步系统高分答案要覆盖“可见性 + 可恢复性 + 可治理性”。

### 简答题 16：当你发现中间件平均耗时上升 3 倍时，如何排查？
**参考答案：**
先对比变更记录 -> 细分耗时（日志、鉴权、序列化、下游调用）-> 采样火焰图定位热点 -> 回滚验证 -> 修复并加监控基线。

**答案解析：** 性能排查必须以数据驱动，避免主观猜测导致误修复。
